Ways to push this further
  1. Redundant input packets. Ristro currently sends just the latest input each tick. Sending the last 3–4 inputs in every packet (classic Source/Quake-style netcode) means a single dropped packet doesn't cause a stale "held" input — the next successful packet fills the gap retroactively instead of waiting a full tick for a fresh one.
  2. Unreliable, unordered transport. Real games run this over UDP-like channels — a WebRTC data channel configured ordered:false, maxRetransmits:0 — instead of TCP-style reliable/ordered delivery, since retransmitting stale input is often worse than just dropping it and waiting for the next tick's fresh one.
  3. Adaptive interpolation delay. Instead of a fixed formula, measure actual round-trip time and jitter continuously (timestamped ping/pong) and retune delayMs live, so it's never larger than the connection actually needs.
  4. Delta compression. Send only the fields that changed since the client's last acknowledged snapshot instead of full state every tick, so more frequent updates fit in the same bandwidth budget.
  5. Dead reckoning. When no new snapshot has arrived in time, extrapolate the remote entity a short distance forward using its last known velocity instead of freezing — trades an occasional visible correction for less perceived staleness.
  6. Lag compensation (server-side rewind). For direct interactions between players — not modeled in this Duel demo — the host can momentarily rewind its own state to what the acting player actually saw, so high-ping players' actions register fairly.
  7. Move the host closer. The cheapest win is often not code at all: regional/edge hosting reduces the actual one-way latency everything above is compensating for in the first place.
  8. Peer-to-peer rollback netcode. Ristro's design here is host-authoritative: every input round-trips through one designated host, even when two players don't actually need that detour. GGPO-style rollback netcode (common in fighting games) removes the host entirely — every peer predicts every player's input, not just its own, and rolls back a few frames to resimulate when a real input disagrees. Round trip then depends only on the distance between the two actual players, not on where a third host happens to sit. This is a different architecture, not a tweak: it needs every peer's simulation to be bit-for-bit deterministic, with no single source of truth to fall back on.

None of this beats physics, and it's worth saying plainly: propagation delay — signal travel time set by distance and medium — is a hard floor nothing above removes, only hides or reduces. The only real way to lower it is a physically faster path (undersea hollow-core fiber, line-of-sight links) — expensive infrastructure, not code. That's the same reason high-frequency trading firms spend fortunes on cable routes between exchanges rather than on cleverer algorithms.
